## Stage sequence

Each functional slice couples necessary VICT–Mastra exposure work with reusable TORI services and the working Studio experience. Use the [cross-repository ownership matrix](CAPABILITY-OWNERSHIP.md); confirm actual API gaps and target packages before V1a and each later runtime slice. Not every slice requires an upstream change. G0/U0 records those dependencies while keeping upstream read-only.

| Stage | User-visible outcome | Required evidence / exit |

V1a/V1b/V1c split the former “V1 Agent Runtime” for tractable delivery; they do not remove any requirement. The first self-authored consumer remains TORI's authoring agent. Stages can contain several bounded slices and repair cycles. VICT Stage 9 Milestone 2 is unrelated to TORI V2 and remains paused.

## G0 — enough compatibility to build the real UI

**Scope:** Exact upstream checkout/artifact resolution; native package/authoring/graph/store probes; logical entity and service ports; simulation origin; test/fixture strategy. Prefer Svelte 5 and TypeScript to align with inspected VICT packages. Choose the minimal compatible host/package manager and lock it after verification.

**Do now:** Verify installed public UI artifacts in a separate consumer; identify canonical document/definition ownership; prove a minimal editable persisted graph using public APIs; record custom-UI gaps; map proposed schema fields without changing VICT contracts.

**Do later:** Full provider/Controller/durable/MCP/API probes at the start of the slice that needs them. G0 records those dependencies but must not delay all UI work until every future backend is proven.

**Stop/hold:** No usable native artifact path, unsupported canonical mapping, or required custom primitive without approval. Complete other preparation and present the concrete dependency fix. Do not install unrelated latest packages or copy private upstream app source to get past the gate.

## U0 — production UI foundation

**Prerequisites:** G0 native installation and minimum contracts demonstrated. Runtime APIs may remain unverified behind explicit simulated ports.

**Scope:** Six core areas, native editing/history, real persistence, typed graph semantics, cross-view identities, fixture scenarios, responsive/accessibility review and owner walkthrough.

**Intermediate review:** Show working candidates during U0: shell/agent authoring first, workflow/creative canvas next, then Session/Trace/provider and capability management. Follow the [checkpoint procedure](FIRST-STAGE.md#intermediate-u0-owner-walkthroughs). Record feedback and iterate within U0; these walkthroughs do not replace final acceptance or authorize runtime work.

**Exit:** Independent engineering criteria complete; owner receives a runnable candidate and gives UI acceptance or concrete changes. Ordinary in-scope UX fixes stay within this stage. No requirement to polish every advanced settings detail before a first runtime slice.

**Stop:** At owner UI review, or a material native UI/contract blocker. No live provider call is necessary to prove U0.

## V1 — small live slices, then advanced mechanisms

V1a begins with one permitted connection → one Studio-defined activation → one real Session turn → one governed read tool → persistent response/trace. Keep this path working while adding Skills/JIT tools, model/mode selection, human requests, processors/budgets and basic evaluation. This is not a release claim until the corresponding T01 criteria are met.

V1b uses the normal UI to create TORI's authoring agent, not a hardcoded privileged backend profile. Its real edits use VICT discovery/canonical-edit/observe/cancel and revision protections. Integrate manual and AI edits into the same source/history rules.

V1c introduces child execution and background durability only after exact-version conformance. Prove child authority, aggregate budgets, cancellation, process restart, stream replay and memory scopes with effect fencing. Surface unsupported resume behavior honestly. Add semantic/observational memory through explicit policy, not by enabling everything by default.

**Stop:** Missing provider/auth eligibility, unreconcilable effect uncertainty, unsupported durable mechanism or required regression failure. A working chat response does not waive the remaining catalog/test requirements.

## V2 — typed executable workflows

Map the existing visual definitions onto Mastra AI workflow and VICT business graph contracts. Keep explicit boundaries between the two runners. Implement data/branch validation and human review with actual suspend/resume. Inject duplicate requests, stale approvals and crashes at effect boundaries. First run deterministic fixtures, then bounded real model/application calls.

**Exit:** T02/T03 with retained source, activation, step receipts and authoritative effect result. **Stop:** Any graph edge claimed executable without a supported mapping, or retries that can silently duplicate protected effects.

## V3 — creative runtime

Select a minimal generation and transform/upscale pair using actual provider support and a bounded agreed call budget. Connect the already-reviewed UI, artifact storage, versioning and provenance. Complete the three-direction creative exercise with real media and user judgement.

**Exit:** T04/T05. **Stop:** Unsupported licensing/credentials/operators, missing asset integrity or owner finds the experience materially unsuitable. Do not drop creative scope because the agent runtime is complete.

## V4 — unify the real journey

Finish the identity and navigation foundations established in U0. Prove explicit creative-to-workflow conversion, real execution, Trace inspection, Session-guided revision, and new output on the original branch. Introduce no second definition or artifact store as a shortcut.

**Exit:** T06 plus affected regressions from T01–T05. **Stop:** Manual copying, divergent IDs/history or authority loss between views.

## V5 — consumers and ongoing work

Inventory actual Quellight code/protocol first. Implement gaps in the correct owning capability under that repository's authorized scope. Verify real shared records and full agreed parity. Include schedules/timezone/misfires, signals/notifications, knowledge extraction, goals and memory policies necessary for Living Book, Compass, Tasks & Commitments, Daily Desk, and habits/routines/practices.

For coding, begin with one contained repository task, then expand to specialists and isolated worktrees. Select direct Mastra coding primitives or an optional supported harness based on evidence; neither path excuses containment or trace gaps. Commit/push/release permissions follow the target repository's scope.

**Exit:** T08/T09 and remaining cross-cutting probes; independent installed consumer proves reusable artifacts/service with no Studio imports. **Stop:** Consumer version mismatch, unavailable domain operations, uncontrolled shell effects or missing external authority. Carry the exact blocked criterion; do not relabel limited parity as complete.

## I-VICT — later adoption

TORI readiness alone does not replace the existing VICT Studio agent. Under a separately accepted integration task, prepare the concrete adapter/install/rollback plan and prove discovery, canonical editing, observation, cancellation, manual-edit preservation, occurrence/revision controls, Undo/Redo and Save/reopen. Keep the existing agent usable until the replacement passes. Revisit measured authoring slowness with new evidence; do not close it merely because the agent changed.

## Gate discipline

Each stage has an exact candidate, deterministic/installed/live/owner evidence as applicable, fresh verification, a state update and next authorized scope. Routine failed candidates are repaired inside the same accepted stage. Do not require a new owner decision for every fix, or silently continue beyond the stage's review boundary.
