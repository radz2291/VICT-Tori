## One turn, three densities

These are three presentations of one saved turn. The example text is illustrative. Rows are collapsed on entry; a status change does not create a second row.

| Quiet | Summary | Full trace (after opening the two rows) |
| --- | --- | --- |
| **You:** What should we research first?<br>**Source access denied.** Private Notes was not read.<br>**Quellight:** Start with demand signals. | **You:** What should we research first?<br>**Working**<br>✓ Read Project Knowledge<br>✓ Ran Research Topics<br>✕ Read Private Notes · Denied<br>**Quellight:** Start with demand signals. | **You:** What should we research first?<br>**Working**<br>✓ Read Project Knowledge<br>✓ Ran Research Topics<br>↳ Input: approved task text. Result: authorized finding, with redaction/preview notes where applicable. Attempt: requested → started → completed. Open Research Topics Run.<br>✕ Read Private Notes · Denied<br>↳ Input: source name if authorized. Result: not read. Receipt: denied before execution; raw reason code in expanded technical detail only.<br>**Quellight:** Start with demand signals. |

Quiet suppresses routine pending, running and successful activity as well as routine navigation for completed steps. It shows brief turn-local warnings for failure, denial, limit, interruption or material uncertainty, including missing or disputed evidence that affects interpretation. If there is no final answer, show the warnings and “No final answer was received” after settlement (or “Waiting for the answer” while live); never invent an assistant reply. An explicitly stopped example is “Stopped before an answer. The status of one action could not be confirmed.” Distinguish user Stop, deadline, and owner/host interruption when proven. An unknown reason stays unknown. Summary shows the same warnings once, alongside collapsed step lines; a disclosure may show a short human description and applicable navigation. Full trace is the same grouping and row order, with the permitted evidence in each disclosure. The stored preference remains presentation-only; switching it never reloads a Run by dispatching work.

## Adapter and step vocabulary

Read the existing authorized Run and `projectRunReport` output, and any already exposed sanitized receipt associated with that same invocation/attempt. Never scan unprojected events for display; never infer success from prose, use live text deltas as accepted content, or restore data the projection excluded. Bind a display observation to a Session message only via its exact Run/turn identity (same rule used for Memory turn attachments). For an unanswered turn, anchor the lifecycle/readout to the original request via a stable display-only turn entry; it is not a persisted message or copyable answer. If no honest turn association can be established, retain the authorized record in Runs Details. Never attach a child's raw evidence to the parent's transcript entry.

Use the report's stream order and answer boundary. Roll up requested, executing, awaiting approval and settled observations into a single line per proven invocation within a Run/stream, with attempt receipts grouped inside. Never coalesce distinct invocations by tool name or fabricate missing correlation; keep unmatched receipts technical and surface material uncertainty as an inline notice. Keep “Working” before the accepted answer and “Continued working” after it only for actual subsequent activity. There is no invented global timeline across streams. Replayed rows update by stable source identity; disputed copies cannot pick an outcome. A completed delegated action shows one row and offers an authorized child Run link; the child's own turn shows its steps. No specialist question or reply row is generated by this V1 slice.

| Operation / evidence | Title and treatment |
| --- | --- |
| Model response lifecycle | Settled success is the actual saved answer, not a second activity line; terminal failure, Stop, deadline or interruption becomes “Could not finish the answer,” “Stopped before an answer,” “Time limit reached,” or “Interrupted” as the evidence allows. “Answer could not be confirmed” for uncertainty. An unclassified failed terminal gets a generic failure title and a technical reason only in Details. |
| Pinned context / read-only tool | “Reading Project Knowledge” → “Read Project Knowledge”; use the authorized resource or tool display name. “Read … · Denied” if refused, “Could not read …” if failed, and “Read … · Not confirmed” for an uncertain effect. If a name cannot be disclosed, use “Read referenced source” or “Run a read-only tool.” |
| Delegation | “Running Research Topics” → “Ran Research Topics”; “Could not run Research Topics” / “Research Topics · Denied” / “Research Topics · Interrupted.” For a known admitted child offer “Open Research Topics Run.” Never equate an absent child or a streamed preliminary result with completion. |
| Authoring operations, if captured in this turn | “Read the definition,” “Proposed a draft change,” “Updated the draft,” using actual admitted operation and confirmed result. “Draft change · Awaiting approval” if applicable. A proposal never becomes a persisted change based on its text. |
| Standing Directive and Memory, where proven | “Checking for a standing directive,” “Standing Directive · Review required,” “Saved standing directive,” “Recalled saved memory,” “Updated saved memory,” or “Forgot saved memory” only for the matching public record. Existing Float review and memory affordances remain actionable; routine history update events are technical. No new activity or memory authority. Generic recognized protected operation: “Action · Awaiting approval,” “Action · Denied,” or “Action · Not confirmed”; do not copy sensitive names or payloads into titles. |
| Other allowed tool | Pending “Run [approved display name],” running “Running …,” complete “Ran …”; unknown tool name is “Run a tool.” Never show a provider tool identifier as the user title. |
| Limit | “Model step limit reached,” “Tool call limit reached,” “Time limit reached,” or “Execution limit reached,” depending on the actual terminal/denial receipt. A counter at its configured maximum alone is not a limit hit. |
| No user meaning / insufficient evidence | Sequence, transport bookkeeping, usage, model retry counters, invocation/attempt IDs, raw error codes, receipt refs, historical labels, and grant bookkeeping belong to Runs Details → Technical evidence. Unknown states, gaps and conflicts have human notices; “Historical Run: detailed activity is unavailable” when the turn cannot support trustworthy activity. Public reasoning remains unavailable; no private chain of thought. |

“Awaiting approval” is pending with an explicit text label, running uses VICT spinner, completed uses ✓ only with completion evidence, failed uses ✕, and plain pending uses the dashed icon. Denied and limit use failed styling with explicit state labels; Stop/interrupt map to cancelled where appropriate and their human title states which. Uncertain uses a labeled status/notice, never ✓ or a spinner that implies work is ongoing. Use explicit text as well as icons and announce material changes without announcing every stream event. Default disclosures are closed after settlement; preserve focus and reader-open evidence. See control gap below for an automatic close on settlement.

**Disclosure contents.** On Full trace, each activity takes one disclosure to reveal authorized Input/Result, ordered stages/attempt receipts, and (where available) reason, sanitized references and related Run link. No raw identifiers outside technical expansion. “Waiting for result” only while active; “Result not retained,” “Access restricted,” “Preview only,” “Redacted,” or “Result could not be confirmed” when supported. No blank-as-success, raw errors, secrets, or new access path. The existing technical Details remains the authoritative place for complete retained diagnostics, historical evidence, gaps/replay conflicts, specialist facts and budgets; navigation to it is read-only. Summary disclosures never expose codes or payloads. Neither mode changes persisted Runs or receipt structure.

## R-7 host deadline proposal

**Approve a governed maximum of 120 seconds.** Propose eligible whole milliseconds `1,000..120,000` and an explicit 90 s initial setting on a newly authored Agent node. That preserves today's ordinary-turn starting policy while making 120 s authorable; the independent Directive 5–120 s pin remains separate. Use the existing Agent Execution surface in this slice. No dependency on the later Memory/Directive node-family schema is necessary: own the field, validation, activation identity and runtime enforcement together here. If the activation schema cannot carry the field without conflicting with another slice, return that specific dependency for disposition rather than showing a UI-only field.

- Validate written values in the editor, server activation fold and stored pin rehydration. Blank on a new/cutover draft, missing, NaN, nonfinite, fractional milliseconds, out-of-range and malformed/altered pins cannot produce an activation or dispatch. Incomplete drafts still save with a field-local error. Explicit migration from known legacy 90 s records is versioned and auditable, never a fallback for malformed new pins; older activated records keep their proven historical policy. Any legacy runtime using an explicit deployment/test override requires provenance rather than an assumed 90 s. Re-activate to change a policy; active Sessions keep the older exact activation.
- At admission, resolve and verify the immutable execution policy, record exact activation ID/revision, acceptedAt, pinned limit and absolute deadlineAt. Arm cancellation from the remaining time and propagate that same deadline through provider attempts, tool/child paths and transport detach/rejoin. Derive remaining time; never restart a full budget on retry or clamp a legal value. Stop terminates the exact Run with a distinct reason. An independent child policy, if applicable, cannot promise more than remaining outer budget: reject the incompatible dispatch or report that constraint explicitly. No silent earlier ordinary-host deadline; surface real provider limits without claiming they are the host's pin. Directive Option C keeps its separate cancellation owner and publication guard.
- Prove with controlled clock and Windows host/browser checks: admissible boundaries, missing/altered/outside values rejected with no activation/run, 120 s follows work at 100 s (including attach/retry), expires at the first boundary at or after 120 s, and a shorter legal pin distinctly expires earlier. Pin + actual deadline + terminal reason agree in the durable Run/receipt; Stop earlier reports Stop. Draft edits, restart/recovery and reattach do not extend deadlines, change valid old pins or replay effects. Keep all accepted Directive tests and confirm that an ordinary turn and an interpretation can have distinct pins.
