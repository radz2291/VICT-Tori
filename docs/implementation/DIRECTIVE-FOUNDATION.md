## Outcome

In Quellight, say “Going forward, give me Orchid updates in three short bullets. Keep that as my preference.” The reply arrives in the agent’s normal voice. A **Memory proposal** card appears on that turn when the interpretation is ready. You can continue chatting while it is pending. Edit the proposal to two short bullets and confirm the exact text. The card shows **Saved** after Studio has the receipt. After restarting Studio, open a fresh Session with the same authorized agent and ask for an Orchid update. The Run identifies the saved revision supplied to Quellight, and the answer uses two short bullets.

“Do you remember what we discussed last week?” is a recall question and creates no save proposal. Disconnect the binding, save and activate the change, then open a Session on that activation. The directive can no longer offer a confirmable card. If you explicitly ask to use that unavailable capability, Studio can explain its availability in the interface. Ordinary chat stays quiet.

### Interpretation and turn ownership

- Start an interpretation only for the latest authenticated operator input on an eligible direct turn. Use a separate, tool-free pass. Earlier authorized exchanges can resolve a reference in that input. Tool results, retrieved content, old turns and model output cannot initiate the operation or select authority, scope, applicability event or action.
- Keep recognition instructions, candidate text and proposal status outside the conversational reply context. Treat the interpreter output as data and validate it against a closed proposal/clarification/no-proposal schema. Require valid text and source references to the authorized inputs. An explicit, persistent preference or fact can produce a proposal. A recall question is ordinary conversation: the interpreter returns no proposal and no clarification. This includes “Do you remember what we talked about last week?”, the walkthrough's “what we discussed last week” variation, and “Ingat lagi apa kita bincang minggu lepas?”. A temporary instruction, quotation, negation, unprompted preference, grant request or out-of-scope edit cannot produce a save proposal. Ambiguity can ask for clarification without promising an unavailable action.
- Release the normal turn and its next-Send slot independently of interpretation. A bounded failure or timeout leaves the ordinary reply usable. Correlate every proposal with the exact originating Session, turn, activation and binding revision. Fence a pending interpretation by that identity so Stop before publication discards even a late valid result. Stopping an older interpretation cannot cancel the next conversational turn. A committed save retains its receipt. Browser reattachment observes existing state. Host restart supplies no automatic interpreter replay or resume claim.
- Slice one has one binding and one semantic. Use the activation-pinned transcript-budget and deadline knobs with the owner-selected defaults. Finalize and prove their supported ranges during implementation; authority, truncation ordering, timing enforcement and cancellation mechanics remain governed. Later watch caps are governed and measured. Future overflow stays visibly inactive until a separate observer is explicitly wired. An opted-in sensitivity setting can affect suggestions only.

### Retention and provenance

**Accepted posture.** Transcript retention is a deployment-level store policy. The deployment contract may choose retention from 30 days through indefinite storage. TORI's provenance, receipts and reconciliation must operate independently of that choice and cannot presume short-lived transcripts. Saved memories and governance receipts are permanent with respect to automatic transcript pruning. Explicit authorized correction, Forget and governed deletion retain their existing semantics. Forget removes the reusable content and leaves content-free tombstones and audit references.

**Current pin limitation.** The baseline Studio supplies 30-day message/thread retention. The installed VICT dedicated-store API requires finite positive ages and caps them at ten years. This public boundary currently rejects indefinite retention. Record indefinite storage as a deployment capability gap to resolve through the appropriate VICT storage decision. The accepted engine posture and source-reference handling can be implemented independently. [Pinned storage boundary](https://github.com/radz2291/vict-02/blob/6b420a3e9eada6f694cc2550debda7753316b5b3/packages/mastra/src/storage.ts)

**Required deployment configuration.** The audit found inline 30-day message/thread and one-day span literals at [server/studio.mjs:278](https://github.com/radz2291/VICT-Tori/blob/fe25266c098840d98cdfa70bd5e4dcbf8a8f7d1d/server/studio.mjs#L278), so the prior deployment-policy posture lacked an actual configuration path. Implement server-owned startup configuration with environment inputs `TORI_MASTRA_MESSAGES_MAX_AGE_MS`, `TORI_MASTRA_THREADS_MAX_AGE_MS`, and `TORI_MASTRA_SPANS_MAX_AGE_MS`, resolved into one typed retention object passed to the installed `createDedicatedMastraStore`. These are deployment-level how-long knobs, explicitly outside the per-agent canvas; the finite bounds and enforcement are governed constants.

Defaults when absent are respectively 2,592,000,000 / 2,592,000,000 / 86,400,000 ms, preserving today's 30d/30d/1d behavior. Each configured value must be a positive finite integer no greater than 315,360,000,000 ms (the helper's ten-year bound). Empty, malformed, zero, negative, fractional, non-finite, over-bound and indefinite values fail clearly before opening/pruning the store. “Clamped to the installed limit” means the accepted configuration range is constrained; do not silently shorten an invalid retention request or silently fall back to defaults. Validate once at startup, expose the resolved nonsecret policy in deployment diagnostics, document restart-to-apply, and test omitted/default/custom/invalid/maximum values. No browser request, canvas node, prompt or tool result can override this deployment policy.

Demonstrate actual pruning through the installed store on disposable data with controlled time, plus saved-memory and receipt survival and operation reconciliation when a cited source is unavailable. Identify the provenance source and any application-domain transcript copies: these Mastra settings govern only the dedicated Mastra store, and must not be presented as proof that every transcript copy was deleted. Prove missing-source handling through the actual source-resolution path, not a detached table fixture. This configuration and coverage evidence is a prerequisite to closing the retention-independence criterion. Saved memories and governance receipts remain independent of automatic transcript pruning. Indefinite retention remains unsupported at this pin; this slice does not upgrade VICT or implement a second pruning engine.

**Open owner fork, non-blocking for slice one.** Current memory revisions hold source-message and contextBasis references. The cited text lives in the conversation store for its configured retention. The owner's recommended direction is to capture the triggering message and cited source spans at confirmation as governed provenance associated with that memory revision and receipt. Forget would purge every such snapshot and retained copy, leaving content-free tombstones. The alternative keeps pointer-only provenance where the deployment retains transcripts indefinitely. Radzi has reserved the choice. The reviewed language/scope concerns in held-out-4 and held-out-25 motivate retaining exact cited spans if snapshots are later chosen; held-out-25's cited message also contains an excluded budget fact, so copying an entire message cannot silently override the confirmed content selection.

Pending that decision, keep the existing pointer-only behavior explicit and preserve an extension path for optional versioned provenance attachments associated with a receipt. Avoid making source text mandatory in an immutable receipt or retaining it in logs. If referenced transcript content has been pruned, show source text unavailable. Preserve the saved memory and its receipt, and reconcile writes using the durable operation records. Snapshot selection, retention and purge behavior require their own accepted decision and evidence before activation. The original transcript follows its deployment policy.
