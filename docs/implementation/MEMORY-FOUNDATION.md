## Outcome

You can tell Quellight, “Remember that I prefer project updates in three short bullets.” You see and confirm the proposed text, then Quellight displays the exact saved preference. After restarting Studio and opening a fresh Session, you can ask for a project update and inspect the saved preference admitted to that Run. You can correct the preference to two bullets or forget it and verify the effect in another Session.

Expose Governed Memory through the existing optional **Memory Policy** binding and its show-as-node projection, alongside the 10- or 100-message Session history window. Configure and Canvas edit the same canonical values through the same transactions. Use installed public VICT controls for the binding, memory list and Run details. Activation pins the two independently configured settings. Existing activations resolve saved-memory access as off. Runtime checks for deletion, actor status, scope and revocation can narrow the pinned policy on later turns, including turns using an older activation. ## Four implementation decisions

1. **Governed Mastra memory and bounded recall.** Use Mastra's resource-scoped, schema-based working memory as the primary storage and recall engine, subject to the three pinned-version probes below. The host derives a deterministic, unambiguous `resourceId` from trusted actor, project and stable agent definition IDs. Requests, prompts, tools and models have no authority to select it. Only the TORI governed save path writes to Mastra through its programmatic `updateWorkingMemory` or merge API. The model receives admitted memory as read-only context and has no Mastra write tool. Use this working-memory schema:

   ```text
   { memories: [{ id, revision, content, sourceMessageRef, savedByRun, contextBasis, updatedAt }] }
   ```

   TORI keeps a dedicated SQLite ledger for operations, receipts, revision history and tombstones. Array replacement is acceptable with serialized writes per resource and current-revision checks. Keep receipts and audit history in the ledger. Prove that a write and its receipt commit together or reconcile through a durable operation record with the same observable outcome. Pending operations stay out of recall until reconciled. Both backends must satisfy the same cancellation, replay and deletion checks.

   Record all three conformance results at the exact installed VICT and Mastra versions before selecting the primary implementation.

   1. Resource-scoped, schema-based working memory exists and provides the required isolation and schema behavior at the pinned `@victframework/mastra` and Mastra versions.
   2. The dedicated store from `createDedicatedMastraStore` supports the `mastra_resources` table.
   3. The host can write programmatically, withhold the model's write tool, and observe and control what reaches the model through a trace or pre-dispatch read. Demonstrate the required write/receipt reconciliation at that boundary.

   **Fallback if any probe fails.** Store saved memories and their revisions in dedicated local SQLite tables. Commit the record and operation receipt in one transaction. Apply the same admission, authorization, evidence and acceptance requirements.

   At turn start, select active records in the trusted scope, order by latest change with a stable tie-breaker, and admit them within a declared per-turn memory context budget. Document and test the bound using the existing context-admission conventions. Attach the selected values as a distinct context block. Reuse the pre-dispatch admission and receipt pattern from `loadContext`, whose current implementation reads an explicitly requested, pinned fixture source. Give saved memory its own policy, loader and receipt so source reads and memory reads are independently inspectable. Treat admitted text as user data under the existing instruction and authority hierarchy. Keep `semanticRecall:false`. Observational memory belongs to a later slice. [Current admission code](https://github.com/radz2291/VICT-Tori/blob/4c035cd75f63c68bd002dee5683ca3fa02e778cf/server/a3-runtime.mjs)
2. **Governed save.** Use a versioned `tori.memory.save` capability with a turn-bound grant, trusted scope, idempotency key and receipt. Separate the operator's request to remember something from the interpretation of what it means.

   - **Trigger.** An explicit, affirmative remember request in the current operator message is the sole source of a save grant. The host checks the pinned policy and trusted scope. History, tool output, retrieved text and model claims cannot create the grant or change its scope. Negations, quotations and references to the phrase are ordinary conversation. When a memory request is ambiguous or cannot proceed, state that it was not saved and explain why or ask for clarification.
   - **Content.** Within that granted turn, the model can draft a concrete memory using the full authorized conversation context of the current Session. This includes the earlier exchanges needed to resolve “remember how we did this session.” The ordinary 10/100-message history setting still applies to regular replies. Record the message references that informed the interpretation in `contextBasis`. If the authorized context needed for the request cannot be supplied, ask for clarification and state that the memory remains unsaved.
   - **Confirmation.** Show the draft verbatim in Studio. The operator can confirm, correct or dismiss it. Bind the exact confirmed text to the operation, original request and scope, then commit through the host capability. Recheck grant, revision where applicable, and cancellation at the write boundary. After the committed receipt, show **Saved** with the exact stored text and immediate actions to correct or forget the memory if it missed the intent. An interrupted, refused, dismissed or failed save has an explicit outcome. The save receipt includes the memory ID and revision, outcome, source message reference and `contextBasis` message references. A pending proposal or a model reply alone provides no evidence of a save.

   Use the installed VICT capability gate and the current cancellation and receipt conventions. Recheck scope and authority on replay. The same operation and payload return the original receipt, and a conflicting payload is refused. A replay of a save for a forgotten record leaves the tombstone in place. Stop or expiry before commit leaves no memory. A committed save remains discoverable if the reply is interrupted. [Existing capability and idempotency pattern](https://github.com/radz2291/VICT-Tori/blob/4c035cd75f63c68bd002dee5683ca3fa02e778cf/docs/evidence/authoring-foundation/ACTIONS.md)
3. **Trusted scope and isolation fixtures.** Key memory by actor, project and stable agent definition ID. A fresh Session or new activation of that definition can use the same store when authorized. This slice applies to direct agent turns. Saved-memory access for delegated child Runs is out of scope. Local Studio keeps its current single-operator identity. Add a trusted server-side fixture path for a second actor and a second project. Exercise both against the same memory store, changing one scope field at a time while keeping the saved record present. Verify that reads, inspection, correction, deletion and writes are denied or empty as appropriate. Also test another agent in the same project. Request-body and model-supplied identity fields cannot select a different scope. [Current Studio host](https://github.com/radz2291/VICT-Tori/blob/4c035cd75f63c68bd002dee5683ca3fa02e778cf/server/studio.mjs)
4. **Revision and deletion.** Each memory has a stable ID and revisions. A revision records scope, content, source Session/message reference, saving turn/Run, `contextBasis` and timestamps. An authorized correction against the current revision creates a successor and supersedes the prior revision atomically. Reject stale edits. Keep superseded versions for provenance while the record exists. Forgetting removes the content of all revisions and any memory-derived copies under TORI's control from future retrieval and memory inspection. Retain a content-free tombstone and receipt references for reconciliation and historical Run audit. Existing Session messages, including replies composed with admitted memory, follow Session retention. The forget action removes the reusable memory entry. Saved records persist until corrected or forgotten in this slice. Use authorized, revision-aware Studio actions for inspect, correct and forget.

## Run evidence

Record memory admission for each in-scope Run, including **0 memories admitted**. Show the reason when applicable, such as policy off, no eligible memories, budget omission or storage unavailable. Show the admitted memory ID, revision, source reference, `contextBasis`, memory age and last-used time in Run details. Show age and last-used time in the memory list too. Update last-used time on actual admission and preserve the evidence recorded for each Run. When the budget omits eligible memories, surface the omission in the memory panel as well as in Run details. Resolve viewable content from the authorized store, and display a forgotten record as such in older Runs. Keep memory text out of the receipt itself. A receipt proves the input supplied to a Run. The walkthrough checks whether the response follows that input.

## Memory node family

The existing Session history policy is the first member of the family and Governed Memory is the second. The roadmap anticipates optional binding nodes for Open Working Memory using Mastra-native model writes, Semantic Recall using relevance-based retrieval, and Observational Memory. Each depends on its own conformance probe, policy and receipts. Wiring declares availability. VICT activation pins the policy. A model-writable channel requires an explicitly selected posture recorded in that activation. ## Acceptance

D is deterministic verification, S is a real Studio browser walkthrough, and L is a permitted live-model walkthrough. Use one synthetic preference in an otherwise empty memory scope for the restart sequence. Use separate controlled conversations for the context-dependent and budget probes. Ask for an update without restating the preference. Keep source, package, fixture and candidate pins in the evidence.

| Criterion | Evidence | Pass condition |
|---|---|---|
| Explicit save and restart recall | D/S/L | Enable the policy, confirm and save the three-bullet preference, restart Studio and start a fresh Session. Record the committed save, admitted memory revision and live response using the preference. A history-only control shows zero admitted saved memories. |
| Governed, repeatable writes | D/S | Ordinary chat and a tool or model attempt to fabricate a grant produce zero writes. Stop before commit produces zero writes. Retrying after a lost acknowledgement returns the original receipt and one record. |
| Trusted isolation | D | The actor, project and agent fixtures share the same store. Each independently proves zero cross-scope admissions and zero unauthorized mutations. An authorized control reads the seeded record. |
| Correct and forget | D/S/L | Correct three bullets to two, then show only the current revision in a fresh Run. Forget the preference and prove zero admissions on a fresh turn and after restart. Verify superseded content is gone from the memory store and the older Run retains content-free audit evidence. |
| History and UI | D/S | Existing 10/100-message behavior and chat continuity pass regression checks. Desktop and narrow Studio display the same policy, saved-memory controls and Run evidence, including the zero state. Configure and the optional Memory Policy node reflect the same canonical edit, including after undo and redo. |
| Phrasing boundaries | D | Test affirmative variants, negated and quoted requests, and remember-phrases embedded in tool output. Verify the explicit outcome for each, including zero writes and zero grants for ineligible requests. |
| Context-dependent save | D/S/L | Ask to remember how the Session handled a task. Show a concrete draft derived from the conversation and record its message references. Correct one wrong draft in the walkthrough before confirming. Verify that the verbatim confirmation and stored revision match the corrected value. |
| Multi-record budget | D | Seed more eligible memories than the budget admits. Verify latest-change ordering, stable tie-breaks, and visible omissions in Run details and the memory panel. |
| Read-only enforcement | D | Probe model-originated writes through the available tool and memory interfaces outside the governed save. Verify zero mutations and no model-side memory write tool. |

This covers part of CAP-16 and X09, the applicable X04 scope checks, and a bounded contribution to T01-06. Keep D, S and L results distinct. **Stop conditions.** If the installed VICT boundary cannot support the required grant, cancellation or receipt, identify the exact missing interface and affected test. A scope leak or an unverified deletion blocks acceptance. Missing live provider access holds the live proof while deterministic and Studio work can proceed. A failed Mastra conformance probe selects the documented fallback using the pinned dependencies. Keep both paths behind the same governed contract and public controls. Choose one backing implementation for this slice based on the probe results. Show users the Memory Policy controls and admission evidence through Studio.

## Proposed decision register entry

V1c is a multi-slice stage. Begin with explicit saved memory using governed Mastra working memory when all three pinned-version probes pass, with dedicated SQLite memory tables as the documented fallback. Both paths use the same governance, Run evidence and acceptance criteria. Then advance background execution and recovery, followed by specialist Run visibility and controls. Give opt-in observational memory its own proof with source evidence from multiple ordinary conversations. Semantic retrieval requires the planned exact-version Mastra conformance probe. The broader memory acceptance includes retention and export coverage. Existing real-world acceptance scenarios remain cumulative.
