This is the delivery proposal for [TORI V1a #3](https://github.com/radz2291/VICT-Tori/issues/3) and the Agent Composition capability audit. The slice IDs below describe proposed delivery order. ## EAC-01 · First delivery · Max output token binding and activation

**Owner:** TORI V1a stage owner. **Slice:** A1, before adding other generation controls.

Two recorded live Coding API turns carried `max_tokens: 4096`. V1a currently edits an inline number on a connected Model Reference. A separate Integer source is a proposed binding. Reuse the public VICT Input and Flow graph operations. Support inline and connected Integer values for the same property, with one effective source, shared Inspector editing, and a deliberate detach back to inline. Leave invocation overrides outside A1.

Resolve the saved Model Reference and Integer at activation. TORI validates whole numbers in its 64–32,768 range. VICT validates `AgentGenerationOptions.maxOutputTokens` and includes it in the canonical profile. Restore that exact activation on each send. The public path is `AgentProfileRegistry` → `pinAgentTurnRunner` → `MastraProductAgent` → Mastra `modelSettings.maxOutputTokens` → provider `max_tokens`. Provider limits apply on the pinned route. Run evidence shows the configured value, the dispatched value when captured, and reported usage separately.

**Installed-consumer acceptance:** In a fresh consumer using packed dependencies, capture the outgoing request from the normal saved-definition → activation → Session path. Activate inline value 4,096, then connect a source and activate 2,048. Verify both request bodies and that the old Session still sends 4,096 after draft edits, reactivation and restart. Exercise incompatible wire rejection, detach, both valid limits and invalid fractional/out-of-range values. Invalid readiness must permit saving the draft and prevent dispatch. Run the binding through public controls in the actual Studio and audit covered control roles. A provider stop caused by reaching the cap is a separate observation from dispatch of the setting. [Recorded live runs](https://github.com/radz2291/VICT-Tori/blob/9fb812fd748ebbeba39a1b16251f0f4aae0b6f4c/docs/evidence/v1a/live-run-evidence.json)

## Acceptance and scope decisions

- A1 proves one complete typed configuration path. A2 adds supported generation and execution controls. A3 proves one context source, scoped memory and one governed read tool. A4 proves structured output validation and one child. These are proposed slices within the baseline, including where capability delivery is later than A1.
- Each slice records the exact product and verifier revisions, tarball hashes, dependency lock, fixture revision, commands, observed receipts, failures and outstanding findings. Use a fresh independent consumer with package-root imports and no workspace aliases. Studio claims additionally require evidence from the running UI using the installed VICT controls. Label deterministic fixture, retained live evidence and fresh permitted live results separately.
- Return any proposed deferral to Radzi with the affected ID, precise provider/VICT/TORI blocker, impact, smallest alternative and proposed return condition. Pending decisions include stop sequences, fallback, hard aggregate token/cost caps, generalized invocation overrides, broader JIT/compaction, native schema generation and live protected writes. These do not silently disappear from the inventory. Scoped memory, basic delegation, structured output and bounded execution controls remain baseline commitments unless Radzi changes scope.
- Owner accepted 0.1.0 and A1 at `c28b28c` and authorized A2. Review the [A2 candidate and scope decision](../evidence/v1a/A2.md) before starting A3. Gate B on VICT #3 is a separate decision.


## A3 acceptance clarification · accepted by Radzi

- **Governed model-step boundary (EAC-05).** Run the same deterministic scenario in a fresh installed consumer with two activated step limits. Pin the same model, read-only Tool Reference, scope and retry policy. With enough steps, prove that a model requests the tool, VICT authorizes one actual read, and a subsequent model call consumes the result and completes. Record outbound model requests, governed tool invocations and the completed Run. With the lower limit, prove that the next model or tool call beyond the budget never dispatches, and retain a terminal Run that identifies the step limit, pinned activation and the calls actually observed. Verify the boundary by capture at both dispatch points. Keep the deadline and outbound-attempt budget from firing first so the proof isolates the step limit. A timeout, retry-cap rejection, unsolicited tool refusal or generic failure does not satisfy this criterion.

- **On-demand context (EAC-07).** Connect one exact read-only source revision. Activation pins the source identity, loader, purpose/scope, demand trigger and budget; it does not read source content. A turn that does not request the source performs zero reads. For one explicit authorized demand through a public installed path, verify one read, actual prompt admission of a synthetic marker within the budget, and a sanitized receipt that identifies source revision, trigger and admitted/omitted result. Denied, unavailable, stale or oversized sources cannot leak content into the prompt, logs or browser. Verify a changed draft or source head does not substitute content for an old Session. This first proof requires one demand path, with automatic retrieval and compaction presented separately for scope review.
- **MCP tool binding (EAC-09 / CAP-19).** Use one read-only tool from one explicitly allowed test MCP server. Verify discovery yields a typed, exact server/tool/schema reference; discovery and connecting do not authorize invocation. Activation pins the reference, approved route and argument contract. At invocation resolve credentials server-side and enforce actor/tool/target scope, schema and deadline through the governed VICT executor. Use a deterministic installed consumer and test MCP server to prove one real protocol call, sanitized correlated tool evidence, denial without a call, and refusal on schema drift or revocation. A static local tool can prove the VICT bridge while the MCP mapping is investigated; it cannot pass MCP acceptance. If the pinned public adapter cannot carry the mapping, return the exact dependency and smallest change for approval before deferring or expanding scope.
