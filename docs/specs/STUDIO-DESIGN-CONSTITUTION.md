# TORI Studio Design Constitution

**Owner-directed UI/UX foundation, consolidated 4 November 2026.** Applies to every Studio page and review surface, including U0 stubs, canvases, nodes, inspectors, menus, dialogs, feedback, Sessions and Runs. This is the **single authority for product-facing visual and interaction conventions**. The [UI Foundation](UI-FOUNDATION.md) remains the functional authoring contract; [UI/UX Verification](UI-UX-VERIFICATION.md) contains repeatable tests; [UI Exceptions](../governance/UI-EXCEPTIONS.md) records approved deviations. This revision preserves the prior V/W/A/R rule IDs used by R1 evidence.

**Requirement** is binding for the owner-directed UI foundation on all applicable review surfaces, including unfinished UI-first previews. **Default** may vary with an explicit UX reason. **Open decision** needs owner resolution before becoming binding. The five-page navigation, consistent panel language and public-VICT coverage rule below are owner-directed decisions; the precise final pixel treatment remains subject to hands-on acceptance. No text here implies that a current build passes or changes the accepted U0 stage boundary. Current user instructions and the existing product/runtime/security contracts take precedence in a genuine conflict.

## Product experience and navigation

- **N1 · Requirement — Task-oriented pages.** TORI Studio's primary user navigation is **Agents, Workflows, Creative, Sessions, Runs**, in that order. The older **Definition graph, Execution trace and Session** triad remains three distinct **underlying concepts and kinds of state**, not three competing top-level page tabs. The five pages share one Studio authoring foundation; they are not five applications.
- **N2 · Requirement — Professional desktop shell.** On desktop, put the conventional menu bar at the **top**, with **File, Edit, View, Insert, Run, Window, Help** and truthful availability. Keep compact project/object context, saved/dirty state and relevant controls near the top. Give the task the central work area, with optional Library, Inspector and Activity docks around it. Anchor the persistent five-page navigator at the **bottom**. Top tabs and a permanent left rail cannot substitute for that primary navigator. DaVinci Resolve is an inspiration for task-oriented workspaces and panel discipline, not a copied skin or a mandate to invent a custom window manager.
- **N3 · Requirement — One docked-panel language.** Optional supporting regions normally include **Library** (left), **Inspector** (right) and **Activity/Console** (bottom). Their **visibility** is governed by a consistent family of labelled toolbar toggles mirrored under **Window**; selected/pressed state, menu check state and actual visibility must agree. Repeated activation shows/hides the panel. A left-collapse icon, an X and a chevron must not independently implement three different styles of the same top-level hide command. Use a chevron for disclosure **inside** a panel, X for a temporary dialog or genuinely closeable document, and panel toggles for workspace-region visibility. Keep visibility controls discoverable while hidden.
- **N4 · Default — Resizable, remembered, relevant.** Supporting panels may resize and remember suitable per-page dimensions/visibility, with Reset Layout. Do not force a lower console into every page. The central stage expands when panels hide; selection, unsaved edits, viewport/camera and keyboard focus remain predictable. Respect deliberate inspector hiding, including when another node is selected; re-open intentionally via its toggle.
- **N5 · Requirement — Clear homes for capabilities.** The primary task page is the entry point; the six functional areas described in [UI Foundation](UI-FOUNDATION.md#2-six-required-areas) remain available as follows:

  | Primary page | Main user task | Supporting capabilities |
  | --- | --- | --- |
  | **Agents** | Build, connect, inspect and tune agent systems | Agent Builder, Skills/Tools/Memory, attached Tests & Evaluation, provider/model settings |
  | **Workflows** | Author typed executable steps, route/control and validate | Workflow Builder, coordinating-engine inspection, run scope |
  | **Creative** | Explore reference material, generate, transform, branch and compare | Creative Canvas, source/result versions and explicit workflow conversion |
  | **Sessions** | Use an authored system, including Quellight, without launching its separate app cover | Conversation, modes, background activity and context inspection |
  | **Runs** | Understand what actually happened | Execution Trace, events, provenance, errors, attempts and effect status |

  **Provider & Capability Management** is a cross-page supporting workspace via appropriate settings/menus/inspectors, not a mandatory sixth primary page. **Test & Evaluation** is accessible from the relevant agent/workflow context. Do not remove either functional area to satisfy the five-page count.
- **N6 · Requirement — Navigation preserves identity.** Moving Agents → Sessions → Runs, Workflows → Runs or Creative → Workflows or Runs must preserve appropriate definition revision, session, run, artifact and selected-result identities. A saved definition, an observed run and an ongoing session must never be conflated. A user-drawn relation cannot fabricate an execution receipt.
- **N7 · Default — Page-specific arrangements.** Agents and Workflows normally prioritize a structure/graph; Creative prioritizes a flexible working canvas and version comparisons; Sessions prioritize the conversation; Runs prioritize trace investigation. Left sources, right inspection and lower activity adapt to the actual task while retaining the same interaction language. Exact measurements are candidates for hands-on evaluation, not fixed architectural constraints.
- **N8 · Requirement — Responsive usability.** On phone/narrow layouts, present one meaningful task at a time and expose supplementary regions through suitable **public VICT** sheet/drawer or equivalent components where covered. Keep the same five page meanings and accessible commands. Do not claim mobile usability from shrinking desktop columns or removing core functions.

## Public VICT UI Foundation controls

- **F1 · Requirement — Public-component-first on every reviewed surface.** **Whenever a public VICT UI Foundation component covers a control's role, TORI MUST use that public component** on **every Studio surface presented for review**, including U0 stubs, demos, graph/node interiors, dialogs, inspectors, overlays, preferences, Sessions and Runs. This is an explicit owner requirement, not optional polish.
- **F2 · Requirement — Roles covered.** Apply F1 to **fixed-choice pickers, buttons, icon buttons, fields, text areas, checkbox/radio/toggle controls, menus, context menus, popovers, dialogs, feedback, validation, progress, loading and status**, plus any other covered role. **Use public VICT Select for a fixed-choice picker when that public component covers it.** No workflow-preview or rich-node exemption.
- **F3 · Requirement — Public means installable.** Verify actual **installed, documented public package exports and versions**. Do not substitute raw browser-native selects, prompts or app-local CSS imitations merely for speed or stubbing. Do not deep-import VICT private source, copy VICT internals, or claim a control is public because a private demo uses it. Underlying semantic HTML rendered *inside* a public VICT component is of course allowed.
- **F4 · Requirement — Exceptions are explicit and approved.** If no usable public VICT component covers a genuinely needed role, document the exact role, package/version/public API checked, why composition cannot meet it, alternatives tested, minimal proposed custom behavior/accessibility contract and upstream/reuse path in [UI Exceptions](../governance/UI-EXCEPTIONS.md). Obtain the owner's decision before accepting the exception. Missing/unavailable packages are **BLOCKED/unverified**, not permission to silently ship a native stand-in.
- **F5 · Requirement — Proof per review surface.** Every reviewed Studio page/state includes a control-role inventory mapping actual source/rendered usage to a public VICT export and version, or a recorded approved exception. Visual resemblance and an agent's assertion alone are not evidence. Use [UI/UX Verification](UI-UX-VERIFICATION.md#2-public-vict-component-provenance) for test steps.
- **F6 · Default — Shared design semantics.** Consume supported VICT tokens and behavioral contracts for focus, hover, selected, busy, disabled, error, color, typography, overlays and responsive adaptation. Custom product composition is normal; duplicating a covered primitive or overriding its role semantics is not.

## Visual language

- **V1 · Requirement.** Give the work the most space and visual weight. In Agents, Workflows, and Creative, the canvas is primary. In Sessions, the conversation takes that role. In Runs, the selected run and its execution trace take that role. Panels support the work, and controls and status stay visually quiet. Use shared VICT components and tokens across the shell, content and overlays.
- **V2 · Default.** Use neutral graphite surfaces with subtle tonal steps and dividers between functional regions. Use a compact type scale, mostly regular weights and consistent spacing. Leave enough room to scan, read and hit controls. Use fewer nested boxes and rounded corners. Reserve the accent for active and selected states and visible focus. Give focus a distinct shape or offset when selection already uses the accent.
- **V3 · Default.** Borrow Weave's canvas-led workspace and contextual placement of tools. Borrow Langflow's readable node headers and grouping of editable fields. Make the agent name the clearest text, align any glyph with it, and place supporting context below. Use the same identity and naming across views. Show how related objects connect or depend on each other where that helps the user decide. [Weave editor](https://help.weavy.ai/en/collections/15341378-weave-s-editor) · [Langflow visual editor](https://docs.langflow.org/concepts-overview)
- **V4 · Open decision.** The owner directed a canvas-first R1, neutral graphite, quiet typography, a single accent and prominent agent names. The precise palette, lavender accent, type scale, spacing and dock proportions remain candidates for explicit visual acceptance. The R1 checkpoint was subsequently accepted on 4 November 2026 as recorded in [Owner Reviews](https://github.com/radz2291/VICT-Tori/blob/1b39881be6568ea7067f7b252f5e84abe7e399ea/docs/evidence/u0/OWNER-REVIEWS.md), but that does **not** by itself freeze every aesthetic choice or prove future pages.

## Workspace and interaction

- **W0 · Requirement — One command model.** Menu item, contextual action, shortcut and toolbar affordance for the same operation must share its semantics, permission/readiness state and feedback. Do not duplicate visually different command systems across pages or activate an unavailable runtime from a decorative control.

- **W1 · Requirement.** Give each capability a predictable home. Put document history, Save and reopen in the document toolbar. Put Add, pan, zoom and fit with the canvas. Put object-specific actions on the node or in its contextual controls. Use the inspector for deeper configuration. Give commands one primary entry point and provide an equivalent keyboard or touch route where needed.
- **W2 · Requirement.** Selection identifies the current object. Focus identifies where keyboard input goes. Editing changes an authored value. Related or containing objects have a separate visual treatment. Keep inline and inspector edits on the same value and history path. Make deselection and dismissal predictable.
- **W3 · Requirement.** Preserve drafts, selection where appropriate, and the camera when panels open or close or the user changes views. A deliberate Fit command may move the camera. Warn before replacing unsaved work and provide a way to retain it. Keep panels in predictable locations and bound scrolling to the relevant region.
- **W4 · Default.** Place the first creation action directly on an empty canvas. Select and reveal a newly created node and take focus to its first useful field. Respect deliberate inspector dismissal during subsequent navigation. Use clear text for unfamiliar or easily confused actions and labelled icons for familiar compact commands.

## Feedback and accessibility

- **A1 · Requirement.** Put feedback beside the field, document or run it concerns. Keep document status in one stable shell location and execution status with the relevant run. Use a toast for background events that need attention. Keep actionable errors visible until resolved, with a concrete next step. Routine feedback should leave the layout steady.
- **A2 · Requirement.** Give icon buttons accessible names and communicate selected, focused, disabled, busy and error states through suitable text, icons or outlines. Tooltips can supplement a control. Essential instructions must also be discoverable by keyboard and touch.
- **A3 · Requirement.** Provide keyboard and pointer paths for selecting, moving, connecting and inspecting nodes as those actions become available. Provide a list or form route where precise canvas gestures are difficult. Keep focus visible and predictable, and return it to the invoking control when menus and dialogs close.
- **A4 · Requirement.** Check actual theme contrast for text, muted labels, ports, edges and focus indicators. Check target sizes and readability at normal working zoom, in narrow windows, at increased browser zoom and with touch. Respect reduced motion.
- **A5 · Requirement.** Announce meaningful outcomes, including a failed save or completed run, without moving focus unless the next step calls for it. Group repeated progress announcements. Clearly label simulated execution in the affected view and record.

## Review and exceptions

- **R0 · Requirement — Review actual work, not a disposable mockup.** Build and review actual working product surfaces. Under the [owner's V1a decision](https://github.com/radz2291/VICT-Tori/issues/3), U0 is reference material and the V1a product begins on a fresh foundation. Real authoring/history/save and honest labelled simulations must stay distinguishable. Judge task flow and professional-software ergonomics separately from evidence that runtime integration is live.

- **R1 · Requirement.** For each checkpoint, identify the candidate, show the relevant screen states and give a short runnable walkthrough. Mark each applicable rule **met**, **gap**, **unverified** or **not yet applicable**. Tie gaps to observable behavior and evidence. Keep engineering results and owner acceptance separate.
- **R2 · Requirement.** Exercise the applicable flow by keyboard and pointer, including a recoverable failure. Inspect the result, focus order, layout stability, contrast and announcement behavior. Include narrow, zoom and touch checks where applicable and record any unverified path.
- **R3 · Requirement.** Record each proposed exception with the rule, affected surface, reason, VICT limitation, alternatives tried, smallest proposed change, accessibility impact and approval status. Keep the evidence in the [UI exception register](../governance/UI-EXCEPTIONS.md). Only the owner can approve a required exception.
